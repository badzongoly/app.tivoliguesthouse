# Finance forms, evidence, Payment Log and activity income — 31 October 2026

Stage: implemented in the existing local checkout, reviewed for this change and tested against the guarded synthetic database. No new migration or ordinary-database financial writes, push or production deployment. Existing local finance activation is retained.

## Owner decisions and acceptance

1. Provider Request replaces the new invoice-number field with a required Phone Number; Work / Receipt Evidence is a required private file upload. Historical invoice fields remain immutable and readable. A provider phone number is a contact, not a unique financial identifier. System request IDs identify each request; duplicate evidence is checked by content hash, amount and cost date under the shared transaction lock. Same phone can serve multiple distinct requests. Independent approval and unique MoMo settlement references remain required.
2. Daily close and daily reopening comments are optional; actor, time and original snapshots remain mandatory and immutable. Weekly/monthly review comments retain their existing requirement.
3. New expense Receipt / Reference is an optional private file upload. Old reference strings remain displayed/exported and survive failed legacy-form retries. Approval keeps the original submission receipt accessible to authorised reviewers.
4. Payment Log lives under Finance & Cash. Removed only the Payments sidebar entry. The old payments.php URL remains protected and redirects with its date filters. The log includes guest receipts, non-guest receipts, explicit recorded expense/provider/payroll payouts, guest refunds and separate internal deposits; inclusive UTC date range, direction filter, 50-row pagination and exact full-period totals. Historical notes and unknown actors/methods remain visible. Payroll detail is excluded without hr.salary. Historical expenses without an explicit payout record remain in Expenses; no payment status is fabricated.
5. Other Income records courtyard events and other paid activities without creating fake bookings. Cash or MoMo receipts have the real recording actor/time and persistent retry identity. A completed service requires confirmation and contributes revenue once; a future-service advance is a receipt only until the recorder or administrator explicitly marks service delivered. MoMo claims use the existing independent-wallet matching, and cash uses the same full next-day deposit register with collision-free source identities.
6. Cash and MoMo are available for new expense settlement. Owner explicitly confirmed: **Keep full cash deposits; track cash expenses separately.** Cash payouts settle approved expenses from separate funding, never subtract from sales cash held, do not reserve wallet references and do not count the expense twice. Provider/payroll payouts remain MoMo-only. Recording an already-completed payment never sends money.

## Security, integrity and affected contracts

New FinanceAttachment validates extension, detected MIME, size (2 MB), PDF signature or image header. Files are AES-GCM encrypted under distinct finance/source contexts using the existing private-vault configuration, outside public assets and excluded from Git. Random immutable storage IDs, fixed generated download filenames, authenticated per-record authorisation, attachment disposition, sandbox/nosniff/no-store headers. Registry metadata and file hash commit atomically with the source command and audit. An encrypted orphan from a rolled-back command has no committed registry and cannot be downloaded; it is not financial evidence and is not exposed. A browser cannot repopulate a file picker after an error; retries require reselecting the same file and preserve the original operation identity.

No table alterations: finance_events, finance_operations, finance_claims and append-only security_audit are reused; expenses/submissions remain the existing authoritative source. Private file metadata adds no plaintext file body to operation fingerprints, financial payloads or logs. Required audit failure rolls back financial rows, evidence registration and operation identity. Posted financial history remains uneditable and undeletable. All relevant writers use the same PDO transaction/security-state lock and server permissions, money arithmetic, CSRF and closed-day/period controls.

New services: FinanceAttachment, FinanceIncome trait, FinancePaymentLog. Changed: FinanceService, ExpenseService; finance/expense controllers and views; protected evidence endpoint/Apache allowlist; legacy Payments redirect; sidebar; focused test fixtures and scripts. No new dependencies or credentials.

Residual limits: evidence authenticity and duplicate economic costs still require human review; file identity is not an invoice identity. No automatic money transfer, merchant API, OCR, antivirus integration, statutory payroll calculation or general financial correction/deletion workflow. Existing completed-stay room-revenue management-estimate limits remain. Recovery must retain finance income events, receipt-source allocation keys, all original costs/approvals/payouts, security audit, private evidence files and the existing encryption key. Use a scoped forward correction; do not revert to readers that ignore activity receipts or drop their deposit obligation.
