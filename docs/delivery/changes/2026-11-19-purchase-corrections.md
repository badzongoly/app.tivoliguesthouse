## Result and contracts

Finance & Cash → Financial Corrections → Purchases & Providers reuses the original posted purchase or approved legacy provider. One private request, exact live preview and one configured-owner approval support corrected cost, a specific original payout amount, received-quantity error or evidenced actual stock return. Return/revise/reject/withdraw, retained earlier proposals, private optional encrypted files, owner review and adjustment notices are included. Original purchases link here; linked expense corrections redirect after source authorization. Legacy provider register and old payment form route to the effective linked balance.

Current cost, recorded paid, still payable and supplier recovery due remain distinct. Cost changes never invent money returned; payout changes never create a second cost. Modern purchases retain their existing bounded partial-payment action. Legacy provider settlement records an evidenced completed partial/full Cash or MoMo payout with actual payer, actual UTC time, independent proof and unique MoMo reference. Separate cash funding preserves the full gross sales-cash deposit obligation. Actual supplier monetary recovery remains outside this recording-correction slice: recovery balances stay visible in source records, owner attention and original requester handovers, with financial-effect-free follow-up notes.

Posting appends pc_posted and the owner decision, persistent finance_operations result and required audit in one serialized PDO transaction. Original expenses, approvals, delivery declarations, purchase_paid/cost_paid rows and original stock movements remain immutable. Stock corrections append signed adjustments or actual out-movements and change the stock cache atomically. Cumulative actual returns, net received quantity, current stock and the original approved/accepted ceiling bound changes. Return references are source-scoped durable finance_claims. Ambiguous intervening counts block a second shortage/return deduction. Missing payout mirrors block further settlement instead of converting a known paid source to unpaid; both directions and exact expense/source/amount/payer/time/reference are checked.

Source/payment/stock versions, server-side roles and CSRF are rechecked. Identical keys/details/files replay the same result; changed details or competing keys cannot duplicate posting. Owner authority is rechecked on correction and existing purchase-payment replay. Cases and encrypted evidence are requester/owner-private. General audit views redact linked provider/purchase settlement proof; public adjustment notices omit private notes/files. Owner review filters the latest lifecycle before pagination, including returned requests revised back to pending.

## Limits, release and recovery

Unknown historical payer/time/proof or stock/source mappings remain evidence-gated. Corrections do not expand existing approved/accepted ceilings, infer valuation or pretend a real supplier refund occurred. Ambiguous counts require reconciliation before another physical deduction. Changed source/stock/payment invalidates an old preview and requires revision. Existing finance/HR/private-evidence/owner setup is required; production host/configuration parity is unverified.

No ordinary database test writes, financial-history deletion/overwrite, new schema activation, Git mutation, push or production deployment occurred. No backup/restore drill is claimed. Retain original and compensating events, stock links, operation keys/results, claims, audits and encrypted files. Retry an uncertain action with the same key/details/evidence. Recover by coordinated forward correction across these readers and writers; never remove posted cases or roll back a single dependent file. An actual release requires the separately authorized target and reviewed full source set.
