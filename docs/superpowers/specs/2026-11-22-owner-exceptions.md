# Owner Exception Register — approval prototype, 22 November 2026

Status: proposed interactive sample, not application implementation or production deployment. No application/database/configuration/Git changes or account grants.

Observed: existing finance cash/custody, CashDiscrepancyService, departure recovery, purchase/provider requests, correction services, private payroll recovery, non-sale stock issues and WeeklyAuditService retain their own source state, authorization, audit and operation identities. Handover owner attention already links unresolved source records. Payroll corrections explicitly do not implement actual monetary recovery; a note cannot settle that liability. Source authority is the configured finance owner, not a name or an administrator role by itself.

Recommendation: one owner-only queue reached from Owner Reports / Overview, not another ledger or ticket-entry workflow. Queue → Show Details → Open Existing Workflow → source result updates the queue. Original case IDs, responsible staff, deadlines, source status and evidence stay authoritative. Sources without a recorded deadline show Not Set. Existing assignment/deadline/follow-up controls remain in their source module. No generic register Approve, Pay, Write Off, Close or Snooze. No new account privileges, external notifications, scheduling or room release in this prototype.

Alternatives considered: separate tickets would duplicate cases and approvals; adding every action to the register would duplicate financial and safety guards. A linked owner queue is the simplest fit. This is the design recommendation supplied for review, not an assertion that the user chose undocumented details.

Open view spans all weeks. Overdue and Needs Your Decision filters are derived from source conditions; no invented risk score or automatic monetary threshold. Rows cover gross cash still due for next-day MoMo deposit, unresolved wallet/custody differences, checked-out-stay recovery, purchase/provider approval or verification, pending charge corrections, private payroll recovery, held stock awaiting actual disposition and audit follow-up. Normal routine records are not exceptions. Amounts describe distinct measures and are not summed into a misleading grand total.

Identity/grouping: canonical (source module, original case/root ID), optionally a source-provided condition identifier for genuinely distinct obligations. Only explicit source relationships are grouped; do not merge by person, amount or date. A deposit already represented by its discrepancy case appears once with the deposit link and remaining obligation. Source progress may remove one blocker and reveal another under the same identity; a partial wallet credit leaves the residual open. A reopened Cash & MoMo dispute returns under the same identity with previous resolution history and prior verified amounts retained. Other sources keep their own supported transitions; a closed weekly audit requires a new audit for a new issue. No due-date edit, follow-up note or mark-done claim can itself resolve the source.

Safety: audit closure remains source-authorized; existing Record Repair closes a Critical fault, staff completion still requires owner verification, and the register never releases a room. Financial: preserve full cash receipts deposit obligation, pay costs separately, keep corrections separate from actual returns/payments and preserve closed snapshots. Payroll monetary recovery is explicitly blocked until its own supported workflow exists; it remains visible for follow-up. Missing/stale source data stays visibly unavailable, never assumed resolved.

Interaction proposal: compact, responsive owner list, Open/Resolved/Activity views, Overdue/Needs Your Decision/Waiting For Staff and category filters, source detail with related records and current follow-up, existing-workflow preview, sample source progress/reopen controls visibly outside normal application actions. Owner-only preview demonstrates denial for another administrator. Source follow-up editing illustrates original assignment/deadline/reason controls only where supported. All CTA transitions focus their action area; native focus is used without added tabindex. Optional host row-spacing control starts Compact.

Implementation controls after approval: read through source permission/attention adapters under a consistent cutoff, carry unresolved records across reporting periods, never fabricate source actor/time or authority, recheck fresh source/dependency versions at actual source commands, retain source-local mandatory atomic audit and durable per-actor operation keys, unique source associations and locked transitions. Opening/rebuilding the owner queue cannot create business records. Idempotency and stale/retry behavior are simulated locally for review; this is not proof of database locking or persistence. Backend activation, new recovery capabilities and external delivery require their own implemented and tested paths.

Prototype sample money uses integer minor units, fictional cases and fixed 22 November 2026 UTC review time. No guest identities, payroll destinations, credentials, SQL dumps or real records are included. Local interaction history records source progress, follow-up before/after, source-unavailable and reopened states. Host state is display context, not an approval or authorization. Chat approval governs implementation.

Executed prototype verification: 33 interaction/layout checks, 12 views at 1024/390/320 px, no runtime exceptions or horizontal overflow. Covered source grouping, overdue filtering, focus, stale-form rejection, same-key replay, partial credit, source-derived resolution, reopened disputes retaining verified amounts, unavailable-source retention, separate cost/payment verification, unsupported payroll recovery, repair/completion/verification separation, owner privacy, retained resolved/activity history and host review-state echo. Desktop queue and mobile private-payroll source screenshots were visually inspected. Testing used a new owned offline browser tab after the optional sandbox preview wrapper did not initialize in that browser; the owned tab and temporary local preview server were closed. No application PHP, database, application file, configuration, account or Git state was modified. No backend transaction, integration or live-data verification is claimed.

Actual implementation must retain each source's extra permissions (including private payroll authority), not merely a general owner flag. An unavailable or unauthorized feed cannot be presented as an empty healthy queue or leak private counts. The prototype's known sample owner is assumed to hold each illustrated source privilege; the other-administrator preview is denied.
